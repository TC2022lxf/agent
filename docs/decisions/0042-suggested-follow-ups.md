# 0042 快捷追问：独立第二次调用，不做成工具

日期：2026-11-09

## 两个东西长得像，职责不同

| | `ask_question` | 快捷追问（follow-ups） |
| --- | --- | --- |
| 是什么 | Tool 调用，在规划链路里 | 消息渲染层附加字段 |
| 何时 | 缺执行必需信息，继续会错 | 本轮已经完成 |
| 对任务 | **阻塞**：拿到回答才能继续 | 不影响本轮任何产出 |
| 失败后果 | 这一轮没有产出 | 没有按钮，对话正常 |
| 归属 | 模型决定 | 后端在 Run 收尾时另发一次请求 |

把追问做成第二个工具，模型会把两件事混起来：要么该问的不问（把问题当建议），
要么建议被当成问题（用户没回答就以为任务没完成）。

## 方案

主回答结束后，`RunExecutor._suggest_followups` 单独调一次模型：

- 输入：本轮 user 文本、本轮 assistant 答复、最近几轮历史
- 输出：`{"questions": ["...", "..."]}`，2–3 条
- 落到 `followups` 事件；时间线把它放在 `follow_ups` 字段，和 `answers` 平级
- 前端渲染成虚线胶囊按钮，点击等于把这段文字当作用户发言发出去

## 为什么是独立调用，不是塞进主回复的 JSON

主回复本身是一个流式 JSON 对象。把「顺便给三条追问」写进同一个契约，会让模型：

1. 在正式回答里重复那些问题（用户已经抱怨过「AI 重复用户提问」）；
2. 为了凑建议而拖长回答；
3. 一旦建议格式出错，整个回答都解析失败。

独立调用的三个实际好处：主回答流不受影响；建议超时/报错直接不展示，不阻塞对话；
可以单独绑一个便宜的模型（`followups.model`，为空则用规划器）。

## 边界

- `ask_question` 那一轮不生成追问：问题还开着，推荐下一个话题等于劝用户跳过它。
- 开关是 `followups.enabled`（控制台可改），默认开。
- 输出要清洗：去掉编号、去重、超长丢弃、不能重复用户刚说过的话。模型给的是建议，不是可信输入。
- 建议是纯文本按钮，不写 Version、不计积分、不碰 `tool_calls`。
