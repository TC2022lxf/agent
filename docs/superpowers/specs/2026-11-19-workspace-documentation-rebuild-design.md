## 1. 目的及已确认意图

用户希望消除旧资料对编程 Agent 的误导，删除旧文档后，以现有代码和测试为依据重建文档主干，完善开发 workspace。用户已明确不采用“将旧文档留在归档目录”的方式。

“旧数据”在本方案中仅指旧文档及其失效说明，不指运行数据库、用户上传、源码、测试、技能、产品样例或设计资源。此范围是已批准方案中的安全边界。

重建服务于用户与编程 Agent 后续持续开发，同时建立可用于未来产品、测试和发布验收的结构；不把尚未完成的验收写成已通过。

### 1.1 人与 Agent 共用 workspace（用户追加确认的核心原则）

Agent workspace 也是 human workspace。文档既用于指引 AI 工作，也用于人类理解项目、审查变更和验证 AI 的交付；不能只优化模型检索而牺牲人的阅读、决策和验收。

- 一套共享事实与契约，多种清晰入口：产品/验收入口、开发入口、Agent 工作入口引用同一正文，不维护互相矛盾的“人版”和“AI 版”。
- 文档驱动工作闭环：人提出目标并确认需求/验收标准 → AI 给出影响范围和执行计划 → AI 交付变更与可复核证据 → 人按同一标准验证并决定是否接受。
- 已批准设计不等于所有反推需求均获认可；人类确认、技术验证和发布批准分开记录。
- 首次阅读者可以快速找到“这是什么、现在能做什么、怎样运行、怎样修改、怎样验收、还有哪些未知”。
- 事实来自代码和执行证据；目标与优先级来自人。AI 不得以“已实现”或自报“完成”替代人类验收。
- 重建的验收场景明确前置条件、操作步骤、可观察结果、证据位置和需要人工判断的项目；测试报告提供复核命令与运行环境，而非仅列绿色结论。

## 2. 方案比较及选择

| 方案 | 权衡 | 决定 |

## 5. 文档真实性与阅读规则

每份人工主干文档标注用途、状态、核验日期和关键代码/测试来源。避免把同一大段规则复制到多处，入口链接至权威正文。人工正文主要使用中文，标识符、命令和生成表格遵循代码原名。

- 现状：以代码、配置、注册表和可复现测试为依据。
- 产品意图：已明确的用户要求与待确认的反推需求区分，不用“已经实现”证明“本来应该这样”。
- 能力状态：区分已实现、占位、未验证、计划；具体缺口有代码位置与后续动作。
- 验证状态：区分自动化通过、真实供应商未验证、人工产品验收未执行、发布待批准。
- 事实冲突：先指出差异并核对，不能无声地选择自己偏好的说法。
- 测试报告记录基线提交及未提交变更范围，不声称对应尚不存在的提交或 tag。
- 对无法由代码判断的目标、质量阈值和发布决策，登记待用户确认，不杜撰答案。

需求与验收采用稳定编号建立追踪，但不为了追求编号覆盖率虚构用例。至少覆盖通用对话与产物、PDP、图像、Canvas、账户/权限、积分/预算、约束/版本、失败/恢复和流式交互。标明不同场景需要 fake、真实模型还是人工验证。

## 6. 协作规则边界

`AGENTS.md` 必须足够短，可作为所有后续编程 Agent 的入口：

1. 先读文档地图和当前能力，不把设计稿、开发计划或示例当成已交付事实。
2. 先定位代码和测试，再改动；同步维护受影响的需求、契约和验证说明。
3. 业务不变量与安全边界指向架构正文，避免重复与漂移。
4. 明确离线验证命令；未经额外授权不调用付费模型，不读取/输出真实密钥，不修改真实数据。
5. 不手改生成文档，不将未经执行的测试写成通过，不将测试通过写成人工验收通过。
6. `skills/` 是产品运行时资产；本轮不删除、搬移或改变其加载方式，不在运行时技能目录混入新的开发工具规则。
7. 不默认提交或推送；本轮只准备可审阅的本地变更。最终集成按用户后续指示进行。

## 7. 最小代码与配置改动范围

这不是业务架构重构。允许的非纯文档改动仅限让新文档可信、可复现：

- 修复 `backend/scripts/gen_docs.py`：包含两个路由模块，按 method + path 去重/检查冲突，正确输出 `public/user/admin` 权限。
- 为生成器新增回归测试：输出与应用实际 OpenAPI 操作及声明权限比对，不能只做“生成结果等于旧文件”的自检。
- 新增标准库文档检查脚本及其测试：校验实际 Markdown 相对链接和锚点、关键入口，并检测受管范围内的已删除旧文档引用。排除依赖、构建、Git、用户数据、产品示例 HTML、生成内容中的非链接文本及第三方许可证，具体排除规则写入测试。
- 清理自有源码注释、说明性 docstring 和文档中的失效引用，指向新正文；不机械替换可执行字符串、系统 Prompt、测试断言、工具契约或产品技能。涉及这些内容时逐项判断并保持原行为，不能以清理为由改变业务语义。
- 配置、README 和 CI 统一明确使用 `pytest -m "not live"`。本轮不改变默认 pytest 选择机制；修正旧的“默认已排除/已有 CI”说明，CI 在实际新增后才作为事实描述。
- 补齐 `.env.example` 中已被代码读取的关键配置说明，不写入实际密钥，不把开发默认值描述为生产配置。
- CI 验证：后端离线测试、生成文档检查、引用检查；前端 `npm ci`、类型检查、测试和构建。无供应商密钥、无付费测试，执行环境从干净依赖安装验证；后端未锁依赖的可重复性局限如实登记，不扩展为依赖升级工程。

不修改 API 行为、认证策略、业务 Prompt、数据库结构、计费逻辑、UI 或 Agent 工具权限；不新增真实支付、自动化调度或其他尚未实现能力。

## 8. 重建与验证流程

批准设计后再编写逐步实施计划。实施先建立事实目录和新的文档入口，再逐份写正文与追踪关系；最后按明确清单移除旧人工材料并同步清理引用。新正文不得直接以旧 ADR 内容为事实复制来源。

生成器和检查器采用先复现缺陷/失败测试，再修复、回归的方式。纯说明性引用更新必须审查 diff，确认没有混入业务行为改动。

最终至少执行并记录：

1. 后端离线测试全套，显式排除 live。
2. 前端类型检查、测试与构建。
3. 生成文档 `--check` 及覆盖完整性回归。
4. 文档链接、入口、删除清单与失效引用检查。
5. 检查实际文件变更和敏感文件范围，不以忽略规则作为安全审计的全部证据。

当前会话前次审计观察到后端 284 通过/7 个 live 排除、前端 112 通过、类型与构建通过。该结果仅是历史基线，本轮报告必须重新执行后填写，不承诺固定数量、不复制成新结果。

CI 配置在本地可检查、可准备，但远程成功与否只有真正推送运行后才能确认；本轮不标记 GitHub CI 已通过。

## 9. 完成标准

- 清单中的九个旧文件不再出现在当前工作树；没有另建归档或混合旧内容快照。

- 产品验收标准、自动化执行报告、人工签署/发布决策分离；未执行状态如实呈现。
- 需求追踪矩阵能够定位真实用例，缺失覆盖显式列为待补，不能编造验收。
- 所有必需本地检查执行并报告真实结果；业务能力不改变，实际用户数据不动。
